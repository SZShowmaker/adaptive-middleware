# 架构：配置、生成代码与运行库怎样配合

这份文档用于理解工程组成和维护边界。只想生成 src-gen 的工程师可先按 [入门指南](GETTING_STARTED.md) 操作，不必先掌握所有内部实现。

## 1. 两个仓库分别做什么

| 仓库 | 维护什么 | 提供给下一层的东西 |
|---|---|---|
| fastdds-build-kit | 第三方源码、依赖版本、编译目标、工具链配置、SDK 构建与打包。 | 某个目标平台的 SDK，以及开发机可运行的 Gen。 |
| adaptive-middleware | JSON 格式、配置界面、生成规则、公共通信运行库、协议绑定和独立样例。 | 完整 src-gen：业务接口、公共模块源码、三平台 SDK 和手册。 |
| 业务工程或契约工程 | 自己的消息定义、App 连接、部署和业务算法。 | 按生成接口运行的应用程序。 |

维护者通过 delivery_sdks 本地配置选择三平台 SDK，生成时随包收集安装产物；不复制 build-kit 源码。应用构建直接引用包内依赖，不要求安装额外 SDK。SDK 为编译提供头文件和库，Gen 只在生成代码时使用。程序运行不依赖配置网页、Java 或 Python 常驻。

CMake 按目标平台选择包内 SDK，检查固定 DDS/CDR 版本、编译器 ID 和主版本，拒绝已加载的外部 DDS targets。维护者仍需验证 ABI、sysroot 和运行库兼容性；工具链路径可配置。

业务使用的普通 C++ 消息对象与 DDS 内部消息对象分开，生成实现负责转换，当前存在复制。公共 CM 接口不要求业务直接操作 DDS 实体；协议相关头文件集中在后端和生成实现中。最终链接仍会依赖 Fast DDS 库，接口隔离不代表没有二进制依赖。

## 3. 为什么区分类型、服务、App 和实例

以两路摄像头为例：两路都可以发送同一种 Frame 类型，但不能把前摄与后摄混成一个数据流。

- 类型定义“每帧有什么数据”。
- 服务接口定义“一组对外提供的消息”，例如 frame 和 health。
- App 定义“本程序提供哪些服务、需要哪些输入”。
- 部署实例定义“本次运行是谁”，并为输入选择具体来源。

当前 Topic 映射为 `amw/v1/<service>/<version>/<instance>/<event-id>`，其中 instance 是部署 provides 中指定的服务实例名，不一定等于 App 实例 ID。查实际字符串应看 routes.json。

运行时按已生成配置创建通信端点，DDS 负责发现和匹配。端点匹配数只是通信状态，不能据此判断对方算法正常、数据新鲜或整个服务健康。

## 4. 生命周期与资源选择

首版以整个 App 为单位 start/stop，同时创建或停止其端点集合。暂不提供单个服务独立发布/撤销、动态选择输入来源或完整的服务发现 API。

每个 Runtime 创建自己的绑定和 Participant，同一个 Runtime 中的端点共用它；当前不会在同进程的多个 Runtime 之间自动复用 Participant。每个通信端点还有自己的有界工作队列和线程。这样容易隔离慢回调，但端点增多时线程、内存和调度成本也会上升，需要按实际规模测量。

部署和策略编译进生成实现，改配置后需要重新生成并构建。详细线程、队列与停止行为见 [运行说明](RUNTIME.md)。

## 5. 后续扩展放在哪里

| 新需求 | 主要修改位置 |
|---|---|
| 增加一种消息 | 业务类型/服务配置，再重新生成，不复制运行库线程代码。 |
| 增加一个 App 实例 | 部署配置，指定独立服务实例及输入来源，再重新生成。 |
| 增加 vsomeip | 新协议绑定、对应编码/发现规则、模型校验、生成器和构建依赖；不是只增加一个页面选项。 |
| Method 请求应答、服务 Field | 扩展模型与公共通信语义，再生成业务接口；不能把现有发布成功当作请求应答完成。 |
| SM、EM 等平台模块 | 新模块通过公共接口使用通信能力，不把系统状态决策写入 DDS 后端。 |

AP 是职责和服务模型的设计参考，当前公开 API 为 amw::cm；并未实现 ara::com 源码兼容、ARXML 或完整标准功能。需求文件保留长期方向，具体已完成范围以 [验证记录](VALIDATION.md) 为准。

## 6. 日志和时间基础模块

amw_log 依赖 amw_time 和私有 XML 解析器，不依赖 CM、DDS 或生成契约。CM 使用已经初始化的进程日志会话；XML 路径和 App 名由进程拥有者提供，CM 不自行寻找配置。普通配置生成仍使用 JSON，日志 XML 属于运行部署参数，只在启动初始化时读取。可用 AMW_BUILD_CM=OFF 独立构建；安装 SDK 支持 COMPONENTS log time，避免日志使用方被迫引入 DDS。

## 7. 单目录交付边界（0.2）

消息模板写入 generated/；公共运行库源码复制到 runtime/；目标平台 SDK 放在 dependencies/；metadata 保存模型/路由；guide 原样附带通用手册。它们与 CMake、日志模板、工具链文件一起纳入生成清单及整体替换/回滚。

仓库和交付包共用 cmake/AmwRuntime.cmake 定义公共 targets，避免两套运行库构建逻辑。包内 amw::app 传递通信及日志/时间依赖，amw_deploy 提供运行库/配置部署。修改运行 XML 后重启生效；网络配置仍编译进生成接口。

每个项目生成一份包，多个应用复用；同一构建仍只允许一份生成契约。公共 API 和 NetworkBinding 边界保持不变，交付方式变化不引入新协议或服务语义。


## 8. QoS 模型、界面与绑定

`tools/amw_tool/qos.py` 是 Fast DDS 3.6.2 参数目录，维护默认值、作用实体、字段 schema、支持条件和生成映射。GUI 获取该目录生成表单；CLI/GUI 共用有效值解析和语义规则。`tools/update_qos_schema.py --check` 检查持久化 schema 是否同步。

源配置保存覆盖，生成时解析默认值、Topic 继承、端点覆盖和实例分组覆盖，输出 `metadata/qos.effective.json` 与私有 `generated/qos.hpp`。生成绑定工厂按实例创建 `fastdds::QosConfig`，在创建 DDS 实体时应用。DDS 类型只出现在绑定头文件与生成实现，公共 CM 和业务 DTO 不引入 DDS 实体。实例共用的 Topic 如果收到冲突配置，生成前拒绝。

配置不会在运行时读取或热更新；没有增加业务线程/队列行为。旧版手工创建绑定的两参数 `create` 仍保留原默认行为。支持范围与未接入项见 [QoS 指南](QOS.md)。

启动时的 `NetworkOptions` 是协议无关的部署参数，生成绑定工厂将其与契约配置合并；它只覆盖接口 IPv4 和发现对端，不提供 Domain、路由或 QoS 覆盖。
