# 后续开发安排

当前可用的是 Fast DDS 发布订阅、JSON 配置、代码生成和本地配置界面。已验证环境见 [VALIDATION.md](VALIDATION.md)，日常使用见 [文档导航](README.md)。下面是计划中的功能，不能在当前配置里提前启用。

## 第二阶段 A：加入 vsomeip 通信绑定

目标是在公共 CM 接口下增加一个与 Fast DDS 并列的后端，使配置界面能够选择底层通信协议。业务消息定义尽量继续共用，但两种协议的发现、编码、可靠性等能力不完全相同，需要明确各自支持的配置。

实施时需要一起完成：

- 服务、实例、Event 编号到 SOME/IP 标识的映射，以及消息编码约定。
- 服务发现、提供/停止服务、订阅恢复、错误和状态处理。
- JSON 格式、校验器、生成器、构建依赖和界面协议选择。
- 两种绑定的共同行为验证，以及协议各自的能力限制说明。

绑定选择最终按整个部署还是按服务配置，在该阶段进一步确定。当前只接受 binding=fastdds，不提供没有实际实现的 vsomeip 选项。

## 已实现：独立终端日志与时间模块

参考旧项目的分级日志和时间工具设计，已实现 amw::log / amw::time：XML 路径由应用指定、启动加载、模块等级覆盖、终端异步输出、有界队列和退出排空、日期/时区时间戳与单调计时。使用说明见 [日志手册](app-guide/LOGGING.md)。

按当前需求不实现日志文件、滚动、DDS 上传或热重载。公开接口独立设计，不兼容旧 E_INFO/E_WARN 宏，不声明 ara::log 兼容。

## 后续根据需求推进

Method 请求应答、服务 Field、SM 状态管理、EM 执行管理和健康监督分别设计职责。当前每端点一线程、静态部署等选择，也应在板端容量验证后评估改进。

AP 对标应逐项记录接口、语义、差异和测试，不能只靠模块名称声明符合标准。新功能的支持状态应先更新验证记录和使用指南，再供业务团队使用。
