# CM 规范差距评估：AUTOSAR R25-11

评估日期：2026-10-16。对象：当前 `main` 工作区的 AMW 0.2.0，包括尚未提交的修改；检查时 HEAD 为 `94321f1`。这是一份**核心能力与架构差距评估**，不是全条款符合性报告，也不授权执行下述改造。

## 1. 结论与使用方式

**当前产品是借鉴 AUTOSAR CM 分层的自研 DDS 发布订阅中间件，尚不能声明为符合 R25-11 的 CM 实现。** 已有类型建模、生成交付、协议隔离、队列、生命周期和 QoS 工程基础；但应用接口、服务控制和 DDS 服务协议存在实质差异，不能通过更换命名空间或添加几个同名函数完成兼容。

| 要回答的问题 | 本次结论 |
|---|---|
| 当前发布订阅能否继续服务现有业务？ | 评估未发现必须因对标而废弃现有交付方式的理由。已有验证范围仍按 VALIDATION 记录；本次不重新证明业务性能或可靠性。 |
| 标准 ara::com 应用能否直接迁移进来？ | 不能。当前生成 App 类、回调及 Result/样本接口不同。 |
| 能否直接与使用标准 AP DDS 绑定的对端通信？ | 当前格式不能直接按该绑定接入；服务发现、Topic 和事件封装均需适配。没有第三方 AP 实现互通证据。 |
| 已完成百分之多少？ | 不给百分比。尚未建立全部适用条款的分母，功能条目数量也不代表规范完成度。 |
| 是否应推翻 GUI、JSON、一个 src-gen 交付？ | 不需要。它们可以继续作为配置入口和交付方式；需要演进的是内部模型、生成接口与通信语义。 |

评审顺序：先看第 3 节差距矩阵，再看第 4 节对架构的影响，最后按第 6 节选择后续开发范围。矩阵中的验收条件均为**建议新增的验收**，不是已经通过的测试。

## 3. 差距矩阵

状态含义：**不同**＝已有实现与目标接口/行为不同；**缺失**＝现有模型和实现没有该能力；**局部基础**＝有可复用部分但不能判符合；**待验证**＝现有证据不足；**条件项**＝由绑定、配置或集成范围决定适用性。各行是条款组，不是完整逐条追溯矩阵。

优先级是改造顺序建议：**P0** 先确定会影响公开契约的设计；**P1** 补选定范围的行为、绑定与证据；**P2** 按集成目标扩展。若项目安全要求使某条件项必需，它直接成为交付门槛，不能因写成 P2 就延期。

## 4. 对当前架构的具体影响

### 4.1 接收流程需要调整，不能只做接口改名

当前流程是 `DDS Listener → 取样/DTO 转换 → CM 队列 → 携带样本的业务回调`。如果要兼容标准接收 API，需要同时提供事件通知、应用调用取样、样本配额和归还；旧的便利回调可以继续由上层封装提供。

尤其需要区分三个容量：DDS 接收缓存、CM 尚未交付队列、应用持有样本额度。当前只有前两类配置。旧接口持有 `shared_ptr` 的习惯与标准样本生命周期前提不同，新增兼容层时必须明确迁移规则，不能无界复制样本来掩盖配额不足。

### 4.2 服务实例需要从 App 生命周期中独立出来

现在 App 装配所有输入输出，一个 Runtime 一起启动停止。推荐引入服务实例的控制对象，管理 offer、find、subscribe 和各自的句柄/状态；App 仍可作为便利的装配入口。`NetworkBinding` 继续隐藏 DDS 实体，但现有仅 writer/reader 的能力不足以表达全部服务发现、撤销和状态通知，需要扩展。

这不会要求用户在 GUI 中每次手工填完全部底层标识。现有自动命名、默认分组、QoS 默认值可以保留；逻辑名称到部署标识的稳定映射由工具管理，并让高级用户检查。业务结构体也继续与 DDS 类型隔离。

### 4.3 DDS 互通必须作为明确的新协议范围

当前自定义 Topic、版本字符串、无 key 的业务 wire 类型构成已有 AMW 协议。标准兼容模式涉及新发现通道/元数据、服务实例标识、数据包装和实体生命周期，旧包与新包不能被默认为直接互通。

这里需要区分目标：CM `SWS_CM_00103/00104`（p.279–280）也允许 `UserDefinedServiceInterfaceDeployment`。**使用 DDS 实现自定义绑定，不会仅因线上格式自定义就自动违反全部 CM 要求。** G17–G21 是针对选择标准 DDS 绑定及互通目标的评估；若产品选择标准应用接口加自定义绑定，需要重新确认这些条款的适用性，并明确不承诺标准 AP DDS 互通。自定义绑定也不能替代 G01–G13 等公共接口和服务语义的补齐。

建议后续设计显式记录协议模式和协议版本，避免偷偷替换旧工程行为。是否保留旧模式、提供网关或要求统一升级，应在具体迁移任务中确定；本次没有修改 JSON 或生成物。

**发现一处需要澄清的规范文本差异：** DDS-C `FO_PRS_DDS_00100`（p.15）给出的 partition 路径使用服务 ID 与实例 ID 之间的 `/`；CM `SWS_CM_11002`（p.179）和 DDS-SD `FO_PRS_DDSSD_00101`（p.14）使用 `_`。这是本次直接对照正文发现的差异，尚未取得勘误或权威解释。选择 partition 方案时不能自行认定某一个必然正确，需与目标对端/规范维护方确认并记录采用规则。当前 AMW 缺少上述整套机制的判断不依赖此差异的解决。

### 4.4 QoS 可视化可以保留，但要增加约束层

“开放给用户的参数有默认值”仍合理。协议内部的发现 Topic、服务实例隔离、订阅缓存等不能任由普通消息策略覆盖。建议按用途管理固定值、可配置值和厂商扩展，在 GUI 中解释禁用或冲突原因；继续让 CLI/GUI 共用同一规则。

这也意味着“开放所有 DDS QoS”与“符合 AUTOSAR CM”不是同一目标。标准应用语义需要服务状态和错误接口，不能靠更多 QoS 输入框替代。

### 4.5 可以保留的工程投入

- 类型/契约/部署分层、统一模型校验、GUI、生成器保护和一个 src-gen 的打包方式。
- 公共 CM/DTO 与 DDS 实体隔离，外部 SDK/Gen 的版本管理。
- 当前生命周期回滚、队列控制、日志诊断和失败测试，作为新实现的基础与回归资产。
- Linux、Windows、ARM 工具链和包内依赖选择；独立日志/时间模块继续使用自身接口，不因 CM 对标而自动改为 ara::log 或时间同步模块。

本次没有把每端点一个线程、复制传输、JSON 配置或内部 Runtime 类本身判为规范缺陷。内部线程架构有实现自由；零拷贝的优化能力与是否实现标准所有权 API 也需要分开判断。CM §4.1.1 还明确列有本地缓冲溢出的规范限制，因此不会凭本项目选择 discard_oldest 就断言违反某个统一标准丢弃策略。

## 5. 尚未覆盖、必须继续核实的内容

1. **全部条款适用性：** 没有穷举 CM 675 页及其引用规范；本表 26 个评估项不是全部 requirement 的分母。标准接口的全部重载、线程/异常要求、Violation 及 API 类型定义仍需逐项展开。
2. **部署与语言绑定：** 未完成 Manifest 元模型、Core 通用要求、语言绑定类型矩阵与 ARXML 工具链审计；也未证明只重链接即可变更部署。
3. **第三方互通：** 没有拿到目标 AP 产品、版本、发现方式及 QoS/安全配置。当前双方都用 AMW 的收发测试不能替代独立对端验收。
4. **平台与资源：** 没有新增 ARM 板端、跨设备网络、长时间运行、资源耗尽、时延上限、消毒器及异常进程退出测试。平台差异不能被同一份源码交付所消除。
5. **规范草案与文本差异：** DDS 协议条款状态、partition 分隔符差异，以及所选 SDK 能否提供所有需要的状态/发现 API，需要在实施前登记并关闭。本文不自行修订规范。

## 6. 建议的后续工作与退出条件

建议先建设**清楚限定的 CM Event 能力范围**，再扩展完整服务模型。这个范围是本项目的阶段目标，不是 AUTOSAR 官方认证等级，也不能对外简称为“CM 已符合”。

| 阶段 | 建议工作 | 完成条件 |
|---|---|---|
| A：固定目标和接口 | 选择以应用源码兼容、DDS 协议互通或两者为目标；确定 API/部署/绑定边界，建立正式条款清单和偏差台账。优先 G01–G09、G14–G18、G26。 | 形成可评审的目标接口、状态机、模型映射和验收清单；不再用“基本对标”作为验收描述。 |
| B：Event 闭环 | 实现服务级生命周期、发现、订阅、通知/轮询、样本所有权、错误、最小发送间隔及选定 DDS 协议路径。 | 覆盖多实例、服务重启、取消竞态、样本耗尽和独立对端互通；GUI 默认配置及单目录交付回归通过。 |
