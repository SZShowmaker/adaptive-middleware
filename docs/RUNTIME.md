# 应用运行时：发送、回调、队列和启停

本文面向调用生成接口的 C++ 开发者。已经生成和编译成功后，仍需要按这些规则使用接口，才能正确处理过载、停止和多线程访问。代码入口见 [接入指南](INTEGRATION.md)。

## 1. 推荐的生命周期

```text
构造 App，选择部署实例
        ↓
注册全部输入消息的回调
        ↓
runtime.start()，检查返回值
        ↓
业务线程提交消息；接收回调在工作线程执行
        ↓
拥有 App 的线程调用 runtime.stop()
        ↓
释放 App 和回调引用的业务资源
```

构造 App、注册回调和 start/stop 应由一个控制线程依次执行，不要并发修改端点配置。首次调用 start 后配置就会冻结，包括启动失败的情况；如果漏注册回调，应修正初始化代码并重新构造 App，不能在原对象上继续补注册。

start 成功表示本地配置的端点和工作线程已创建，不表示远端已上线。重复 start 在已运行时返回成功，stop 可以重复调用；完成 stop 后可以用同一组端点重新 start。启动失败会回滚已创建资源，原因见 Result.detail。

接收回调可能在启动过程中就开始运行，特别是接收到历史样本时。因此回调使用的业务对象应在调用 start 前准备好。

## 2. try_publish 成功到底说明什么

发送过程有几个先后阶段：

```text
业务调用 try_publish → 中间件队列接纳 → 发送线程调用 DDS write
                    → 网络/本机传输 → 对方接收 → 对方业务处理
```

try_publish 返回成功只对应“队列接纳”。它不会等待对方处理，也不能证明对方此时在线。DDS 写入在另一个线程进行，失败累计在 send_failed 中。DDS reliable 策略也不是业务执行确认；若业务要求确认，需要额外的应用协议。

| 常见返回 Code | 含义与处理方向 |
|---|---|
| ok | 已接纳入队，可继续业务处理，同时按需求监控后续统计。 |
| not_running | 端点尚未启动或已停止，检查生命周期。 |
| queue_full | 使用 reject 策略时队列已满，应按业务决定丢弃、稍后重试或报告异常。 |
| invalid_sample | 类型边界不合法，或消息估算大小超过队列字节预算；查看 detail 和源配置。 |

try_publish 按值接收消息，可以传入对象或 std::move 后的对象。中间件用带所有权的只读指针保存样本，业务不应再通过其他别名修改同一份数据。调用中仍有分配和锁操作，不承诺硬实时、零分配或绝对不阻塞；内存分配失败等 C++ 异常也不能等同于上述普通状态码。

## 3. 接收回调在哪个线程运行

每个订阅端点有自己的队列和工作线程，同一订阅内依次处理。不同订阅的回调可能并发执行，即使它们属于同一个 App。如果同时访问业务共享变量，应使用锁、原子量或业务自己的串行调度方式。

回调收到 `shared_ptr<const T>`，指向一条完整消息。需要延后处理时可以保留这个 shared_ptr，不能只留下对象地址再丢掉所有拥有者。长期持有很多样本会增加业务内存，接收队列上限不能约束这些已被业务保存的数据。

回调抛出异常时会计入 callback_failed，工作线程继续处理后续样本。应由业务自行记录具体异常原因，当前计数器不保存异常文本。

## 4. 队列满了怎么处理

每个端点同时受 queue_samples 和 queue_bytes 限制。字节数由消息数据和容器容量估算，不等于进程总内存；DDS 自身缓存、正在执行的消息和业务保留的样本还会占用内存。

| overflow 策略 | 满队列时的行为 | 适合怎样理解 |
|---|---|---|
| discard_oldest | 丢弃队列中最旧样本，为新样本腾出位置，累计 replaced。 | 允许跳过中间状态、关注较新值的状态数据。 |
| reject | 不接纳新样本，累计 rejected。发送方调用会得到 queue_full。 | 需要显式处理过载的场景；策略本身仍不能保证不丢消息。 |

例如接收回调处理很慢，普通状态流可替换旧队列样本；若是每条都必须处理的记录或事件流，需要同时设计处理能力、背压或持久化，不能仅把 DDS 改成 reliable。

## 5. 正确停止和释放资源

控制线程调用 stop 时，会停止接纳新样本，丢弃尚未处理的队列内容，然后等待已经开始的发送/回调结束，再释放通信端点。**stop 不会把所有队列内容发送完。** 不要发布一条消息后立即 stop 并据此判断发送失败。

回调中需要发起停止时用 request_stop。它发出停止请求，但不等待自己的线程退出；由拥有 App 的控制线程随后调用 stop 完成等待。若回调直接调用 stop，会返回 would_deadlock，同时提出停止请求。

不要在 App 自己的回调中销毁该 App；当前实现检测到这种用法会终止进程。回调应通知拥有者，在外部完成停止和销毁。若回调无限等待且不返回，外部 stop 也会继续等待，业务需提供合作退出机制。

运行中可以调用 try_publish、查询指标和 request_stop；它们不替代 App 对象的生命周期管理，不要让其他线程在对象销毁后继续使用它。

## 6. 怎样看统计与时间

发布接口提供 metrics()/matches()，Runtime 也可以用端点键查询，例如 demo 中的 `app.runtime.metrics("perception.frame")`。端点键使用点号，C++ 发布成员名使用下划线；实际键可查 routes.json。

| 指标 | 当前实现记录的含义 |
|---|---|
| submitted | 通过初始类型/字段检查、进入队列提交逻辑的次数；早期非法样本不会计入。 |
| accepted / received | accepted 是入队次数；接收端入队还会增加 received。它们不是全网收到/发出的总数。 |
| replaced | 为新样本让位而丢弃的旧队列样本数。 |
| rejected | 未接纳的提交和停止时丢弃的待处理样本都会计入，不能单独当作网络丢包率。 |
| sent / send_failed | DDS write 成功或失败的次数；sent 不代表对方业务已收到。 |
| delivered / callback_failed | 回调正常返回或抛出异常的次数。 |
| queue_high_water / queued_bytes | 队列历史最高样本数、当前排队数据的估算字节数。 |
| matches() | 此端点当前 DDS 匹配数；不表示整套服务或对方业务健康。 |

指标在同一 Runtime 对象内累计，stop/start 不会清零。查询不存在的端点键当前返回零值，因此应先核对 routes.json 中的键，避免把拼写错误当作“没有流量”。

匹配查询先在 CM 锁内保留端点引用，释放锁后调用绑定，避免与 DDS 接收回调形成反向加锁。
如果查询与 stop 重叠，查询中的端点会存活到查询结束，返回值可能属于停止前的端点；
匹配数不能用作停止完成的同步信号，App/Runtime 本身仍必须覆盖查询的生命周期。

SampleInfo 中 receive_steady_ns 是本机单调时钟接收时间；dds_source_unix_ns 是 DDS 源时间，只有 source_time_valid 为真时才应使用。它们不自动等于传感器采集时间；跨主机分析时延还需要明确业务时间字段和时钟同步。

## 7. 传输模式的范围

当前后端使用 UDP，可配置增加普通 Shared Memory Transport；Data-sharing 默认关闭，可在 QoS 表单中配置 off/auto/on，约束和生效条件见 [QoS 指南](QOS.md)。共享内存是否实际参与传输取决于两端环境；2026-10-20 已在 Linux x64 隔离环境验证普通 SHM 与 UDP 双订阅，并通过屏蔽 UDP 业务数据确认同机 SHM 路径。同日 ARM64 板端通过 SHM 接收栈定位并修复匹配查询死锁，修复后完成 180 秒连续接收与定时停止，具体范围见 [验证记录](VALIDATION.md)。这些结果不代表跨设备、长期负载或 Data-sharing 已验证。当前没有零拷贝、RPC、恰好一次处理或硬实时保证，协议扩展计划见 [路线图](ROADMAP.md)。

## 启动网络覆盖

生成 App 的可选第二参数 `amw::cm::NetworkOptions` 仅覆盖本机 IPv4 网卡和初始发现对端。未设置继承生成值，显式空值清空；构造时复制，启动时校验，不支持热更新。Domain、Topic 和 QoS 仍由工程生成。调用与错误处理见 [应用 API](app-guide/API.md#启动时选择本机网络)。
