## 2. 背景、环境与产品边界

目标是独立的中间件产品与配置生成工具链，支持同 SoC 跨进程及跨设备通信。历史感知项目用于理解使用场景，其旧接口、Topic、QoS、binary 布局和上位机实现不约束本产品。新消费者与生产者按中间件发布的契约接入；不在 CM 内实现业务兼容层。

固定依赖基准：Fast DDS **3.6.2**（实际库版本 **3.6.2.0**）、Fast CDR **2.3.6**、Fast DDS-Gen **4.3.0**。build-kit 安装位置由本机配置指定，产品配置不能写死开发者路径。

中间件独立建仓，通过配置消费 build-kit SDK；首版从自身类型描述、样例应用和验收用例完成全链路，不依赖原感知仓库或上位机。实际业务适配在产品接口稳定后由各项目推进，属于后续独立任务。

| 部分 | 负责 | 不承担的职责 |
|---|---|---|
| fastdds-build-kit | 固定依赖、源码构建、生成器准备、跨平台 SDK 打包 | 业务 App 拓扑与系统状态决策 |
| CM 运行库 | 实体生命周期、发布订阅、线程/队列、状态、错误、配置 | 感知算法、自动推导业务逻辑 |
| 配置模型与生成器 | 校验类型和连接，生成 IDL、类型绑定、App 通信接口及配置 | 自动编写业务处理算法 |
| 可视化编辑器 | 编辑同一配置模型、预览、诊断、调用生成器 | 另实现一套独立的生成规则 |
| 接口契约包 | 消息类型、服务接口与版本定义、生成类型绑定 | 业务内部结构体转换、复制 CM 核心实现 |
| 后续 SM | 根据业务和通信状态决定运行、降级、恢复 | 反向嵌入 CM 核心逻辑 |

建议 CM 采用 C++17，支持 Linux x86_64、AArch64 Linux 和 Windows x64。编辑器面向 Windows 和 Linux 开发电脑，不在嵌入式板上运行。GUI 框架、生成器语言、仓库名称暂不限定。

配置工具是开发阶段工具。生成后的 App 必须能独立运行，不依赖编辑器或生成服务常驻；GUI 中的连线本身不会创建运行时中央转发进程。

### 2.1 对标 AP 的具体层次

以 **AUTOSAR AP R25-11** 的公开规范作为当前固定设计参考，后续有计划地更新参考版本。Fast DDS 版本锁与 AP 参考版本分别管理。这里的对标包括职责、服务模型、接口语义和工程质量；逐项记录实现范围，而不是仅采用 CM/SM 名称。

| 对标维度 | 本产品的设计与阶段 |
|---|---|
| 服务化通信 | 首版模型包含服务接口/实例及 Event，提供者/消费者生成接口；以后增加 Method 与服务 Field。 |
| 部署与绑定分离 | 消息类型、服务契约、App 使用关系、部署实例和 DDS 映射分层，改主机或网卡不改消息类型。 |
| 生命周期与发现 | 首版明确提供/停止提供、订阅/取消、实例可用性及恢复语义；首版按配置绑定目标实例，完整动态选源后续扩展。 |
| 平台模块边界 | CM 管通信；后续 SM 作状态决策，EM 负责应用执行，健康监督与日志等按职责独立扩展。 |
| 接口质量 | 显式错误、数据所有权、线程与退出契约、版本管理、自动化生成及跨平台验收。 |
| 标准接口与互通 | API 使用本产品命名空间与已定义语义。ara::com 源码接口兼容、ARXML 交换、特定 AP DDS wire 映射及全平台符合性分别列为未实现项；不由同名接口推导支持。 |

架构对标表、实现状态和差异记录是工程交付的一部分。首版不增加占位方法并返回成功来冒充完整功能；未来遇到不支持的模型元素应明确报错。

## 3. 必须统一的概念

| 概念 | 定义与约束 |
|---|---|
| 类型 Type | 一条消息的结构，如 PerceptionFrame；不等同 Topic，也不属于某台设备。 |
| 服务接口 ServiceInterface | 有名称和版本的通信契约，首版包含若干 Event；独立于提供它的 App。 |
| Event | 发布订阅成员，每个样本携带一条完整类型化消息；不是结构体中的单个字段，也不限定为低频离散事件。 |
| 服务实例 ServiceInstance | 一个服务接口的可区分提供实例；与 App 实例、主机、DDS Participant 分别建模。 |
| Provided/Required 服务端口 | App 对服务的提供或使用声明；实例绑定由部署配置解析。 |
| 字段 Field / 信号 | 消息内部成员，如 vehicle_speed；不默认对应独立 DDS 端点。 |
| App 定义 | 应用的通信接口契约，描述它有哪些输入/输出；不是工具生成完整业务程序的承诺。 |
| App 实例 | 某个 App 定义部署后的一份运行实例；同一 App 可有多个实例。 |
| 主机 Host | 部署位置与平台，如 SoC 或 Windows PC；同主机通信还需考虑命名空间和权限。 |
| 输出端口 Output | GUI 中某 App 提供的一个 Event 消息流；从所提供服务接口派生，不重复维护类型定义。一个 App 可提供多个服务及多个 Event。 |
| 输入端口 Input | GUI 中某 App 选择订阅的完整 Event 消息，属于一个 Required 服务端口。 |
| 连接 Connection | 输入到输出的设计绑定，包含源实例选择与策略；不是传输层访问控制。 |
| Topic/类型绑定 | 根据端口与部署配置解析出的实际 DDS Topic 名和类型名。 |
| 字段视图 Field view | 对收到的完整消息提取字段，方便业务使用；不代表网络只传该字段。 |

**类型、输出端口、App 必须分开建模。** 同一个类型可以用于多个输出，例如前摄与后摄都发布相同类型；不能因此把它们合并成一个流。同一输出也可被多个 App 订阅。

第一版连接支持一对多发布订阅，每个 Required 服务端口解析到一个明确服务实例，其 Event 可分别选择订阅。配置界面可通过点选源 App 输出完成绑定；运行时目标是服务实例，不把远端进程名写进类型 API。多源融合、动态多实例选择后续显式扩展，不能因 Topic 重名而偶然发生。

### 3.1 可扩展性的可检查要求

| 编号 | 要求 |
|---|---|
| ARCH-01 | 类型、服务接口、App 提供/使用、部署实例、传输绑定分别建模。输入输出是便捷视图，不能成为缺失服务语义的独立第二套模型。 |
| ARCH-02 | 公共强类型接口通过稳定类型/服务/成员标识生成；服务调用方不需要持有 DDS 实体或硬编码对方 App 名/IP。 |
| ARCH-03 | 类型/成员版本、错误域、资源句柄、时间与执行器采用一致契约，CM 对 SM/EM 无反向依赖；core 只放已有多个模块确需共享的能力。 |
| ARCH-04 | 模型区分 Event、Method、服务 Field；首版仅支持 Event。以后加入 Method 的请求/响应、Field 的访问/通知时，可扩展模型和模板，不重写原 Event 消费者。当前非空的不支持元素明确报错。 |
| ARCH-05 | 运行层保留传输绑定边界，首版只实现 Fast DDS；先验证边界与依赖方向，不预建所有协议后端/插件。新后端语义与能力必须显式报告，不能假设 DDS QoS 普遍适用。 |
| ARCH-06 | GUI/CLI 共用规范化模型和生成核心；前端布局、IDL 映射、模板、运行库可以分别演进，并由版本兼容检查约束。 |
| ARCH-07 | 扩展设计通过具体场景评审：新增 Event、服务第二实例、部署变化、新增 Method/Field、引入 SM；列出变化文件与不受影响接口，不用继承层数或预留空类证明扩展性。 |

AUTOSAR 服务 **Field** 表示具有访问/通知语义的服务属性，与 JSON 类型结构体中的字段不同；后续增加服务 Field 不改变已确认的“完整消息订阅”粒度。

## 4. 首版范围与优先级

P0 表示首个可用于项目的版本必须具备，P1 表示首版落地后扩展，P2 表示长期方向。P0 仍须按第 15 节分阶段完成。

| 优先级 | 内容 |
|---|---|
| P0 | 标准类型描述导入；类型树与搜索；App/端口编辑；输入输出绑定；消息级订阅；部署与通信配置。 |
| P0 | 同一模型的 CLI 校验/生成；IDL + 官方 DDS 类型代码 + App 接口 + 配置 + 构建入口 + 生成清单。 |
| P0 | CM 发布订阅、有界队列、明确线程/生命周期、错误与可观测状态；Linux/ARM/Windows 构建。 |
| P0 | 服务接口/实例/Event 的最小模型及生命周期；独立多 App、多类型、多订阅者的端到端样例与架构扩展评审。 |
| P1 | 类型演进辅助、按后续明确需求增加受控 C/C++ 头文件或 IDL 导入器。 |
| P1 | 经真实需求确认后的请求应答、命令关联/超时/幂等支持、更多传输与性能优化。 |
| P2 | SM/EM 等平台模块、服务能力完善、动态实例选择、动态配置热更新、零拷贝专项。 |

字段树浏览、搜索属于 P0，便于查看完整消息内容。字段视图代码生成和字段级传输拆分均不属于当前交付范围；不再把字段视图作为默认 P1 工作。后续只有新增明确需求时才调整范围。

现有上位机波形/MF4 功能不并入配置工具首版。CM 应提供数据与时间元信息供记录工具使用，完整录制链路的文件格式/切分仍是独立需求。

## 5. 类型文件导入与契约

### 5.1 已确定的输入路线与设计责任

用户已确定首版以固定格式 JSON 为权威输入，并授权设计方制定具体定义和使用方法。本方案采用 UTF-8 **JSON 类型描述 + JSON Schema 结构校验 + 语义校验**。类型描述是源文件，IDL 是派生产物，不同时把自动生成的 IDL 当成第二个可编辑源。无需再向用户确认 JSON 与 C 头文件/IDL 的格式选择。

设计方负责将下列约定落实为正式 v1 格式规范、机器可读 schema、合法/非法样例及使用指南：

- 类型契约文件使用 `.cmtypes.json`，App/端口/连接使用 `project.cm.json`，部署配置另存；共享内容使用相对路径，个人工具链/SDK 路径放本地覆盖文件。
- 格式版本、类型版本、稳定类型/成员标识分别管理；类型引用必须可唯一解析，不根据导入顺序猜测。
- 类型库支持一个文件多个类型及嵌套引用；成员名称、单位和说明的用途明确，类型兼容不能仅按名称判断。
- 拒绝重复 JSON 键、未知字段（正式定义的扩展区除外）和隐式数值截断；超出常见 JSON 消费端精确整数范围的契约常量须规定无损编码及校验，不依赖 GUI 浮点数转换。
- 定义数组/序列/字符串边界、枚举值、命名冲突、默认规则、IDL 映射、错误编号和规范迁移方式；不能以一份 JSON 示例替代完整规范。
- 界面编辑与手工编辑遵循同一规范。保存稳定排序/格式，避免无意义的 Git 差异；不改变具有协议意义的成员顺序或标识。

以上属于已经授权的技术设计工作，不需逐字段向用户索取规则。正式 schema 与映射仍需在实现阶段前完成和验证；本轮不把候选示例宣称为已经实现的解析契约。

GUI 和 CLI 使用同一个解析器、同一份模型与校验规则。后续导入 IDL/C 头文件时，应经过专用导入器进入统一模型，明确支持子集和损失信息；不能承诺解析任意 C++、宏、编译条件、指针或 ABI。

| 编号 | 要求 |
|---|---|
| TYPE-01 | 文件带格式版本；类型有稳定标识、命名空间、名称、版本、说明；界面显示来源和摘要。 |
| TYPE-02 | 支持固定宽度整数、bool、float32/float64、枚举、嵌套结构体、定长数组、有上限 sequence/string。精确定义到 IDL 的映射。 |
| TYPE-03 | 字段具有稳定成员标识、名称、类型及可选单位/说明/有效范围；这些元数据随生成产物保存。 |
| TYPE-04 | 首版要求集合声明资源边界；无界集合暂不支持并明确报错，未来有实际需要时通过能力/策略扩展。不能把 bounded 直接标记成零拷贝。 |
| TYPE-05 | 拒绝重复类型/成员 ID、未知引用、循环值类型、不合法标识符、目标语言名称冲突、非法边界等；不静默猜测或截断。 |
| TYPE-06 | 导入先预览新增/冲突/变更及受影响端口，再提交模型更新；失败保留原工程。重复导入相同内容不产生重复类型。 |
| TYPE-07 | 不执行描述文件内的脚本；生成时使用结构化进程参数，正确处理空格、中文、反斜杠路径。 |
| TYPE-08 | 不把固定宽度类型与原生 long、size_t 等平台相关类型混用；范围、枚举值和单位转换必须显式定义。 |

### 5.2 历史候选类型示例（不是当前输入模板）

下面是**待落地为正式 schema 的候选格式**，不是已有工具能识别的文件。ID、版本与成员 ID 都参与契约管理，字段显示名称不能代替稳定标识。

```json
{
  "format_version": 1,
  "package": "example.perception",
  "types": [
    {
      "id": "example.perception.DetectedObject",
      "version": "1.0.0",
      "kind": "struct",
      "fields": [
        {"id": 1, "name": "object_id", "type": "uint32"},
        {"id": 2, "name": "distance", "type": "float32", "unit": "m"}
      ]
    },
    {
      "id": "example.perception.PerceptionFrame",
      "version": "1.0.0",
      "kind": "struct",
      "fields": [
        {"id": 1, "name": "sequence", "type": "uint64"},
        {"id": 2, "name": "vehicle_speed", "type": "float32", "unit": "m/s"},
        {
          "id": 3,
          "name": "objects",
          "type": {
            "kind": "sequence",
            "element": {"ref": "example.perception.DetectedObject", "version": "1.0.0"},
            "max_length": 128
          }
        }
      ]
    },
    {
      "id": "example.perception.HealthStatus",
      "version": "1.0.0",
      "kind": "struct",
      "fields": [
        {"id": 1, "name": "healthy", "type": "bool"},
        {"id": 2, "name": "error_code", "type": "uint32"}
      ]
    }
  ]
}
```

本例未定义采集时间；工具不能自动宣称 sequence 是跨重启唯一序号，也不能自行把接收时间填成采集时间。实际接口要补充时间与源实例语义。

### 5.3 版本变化

TYPE-09：格式版本、业务类型版本、DDS wire 类型标识/扩展规则、生成器版本分别管理。兼容性不能仅按语义版本号或 sizeof 判断。

TYPE-10：变更类型时展示所有受影响 App/端口；删除、改类型、改容量、重命名、单位变化分别报告。首版未能证明兼容的变化标记“需要验证/重新发布”，不得宣称任意字段增删自动互通。IDL extensibility 策略需显式选择并通过新旧端互通验证；成员 ID 不因字段排序变化而重新分配。

## 7. “选择输入信号”的准确含义

**FIELD-01，P0，用户已确认：** 输入按完整消息/输出端口订阅。UI 能展开字段树，搜索 vehicle_speed 或 objects[].distance，显示类型、单位、所属消息及数组/序列边界；字段仅供查看，不提供易被误解为订阅设置的字段复选框。

**FIELD-02，范围外的后续说明：** 若未来要求字段视图，可生成访问函数，但底层仍接收同一消息。多个选中字段来自同一样本时，应保留共同样本身份；序列成员访问需要实际长度检查，空序列/越界有明确结果。固定下标不代表同一物理目标，按 object_id 跟踪属于额外业务语义。当前不要求实现。

**FIELD-03，后续按需：** 若只想传 speed，须定义独立 Speed 消息及输出端口，并由生产者或显式适配应用发布。工具可以辅助声明，不能偷偷拆分原协议或凭空生成数据处理进程。

ContentFilteredTopic 按条件选择样本，不等同把一个结构体裁成若干字段。不同消息字段也不因在界面中一起勾选，就具备相同采集时刻或原子一致性。

建议 P0 页面组成如下，具体布局与技术栈可调整：

| 页面/区域 | 必要能力 |

UI-03：大字段树按需展开/渲染；搜索覆盖嵌套字段，结果显示完整路径。具体容量/响应时间预算见第 16 节，不用一个演示小模型代表已满足大工程。

UI-04：生成在后台运行，可查看完整工具日志；操作不能冻结编辑器。生成用开始时的模型快照，期间编辑须标记生成物已落后于当前内容。

UI-05：不依赖云服务上传业务模型；首次工具准备允许按现有 build-kit 规则联网。工具与依赖就绪后，本地校验/生成应支持离线执行。桌面应用或本地 Web 形态待选，均应具备所需文件访问能力。

## 9. 配置模型与代码生成流水线

```text
类型描述 + App/端口/连接 + 部署/策略
                  ↓
         解析、规范化模型、语义校验
                  ↓
     生成 IDL + 接口描述 + 运行配置
                  ↓
          Fast DDS-Gen 4.3.0
                  ↓
   官方类型/序列化代码 + 自定义 App 接口绑定
                  ↓
          构建入口、清单与诊断报告
```

| 编号 | 要求 |
|---|---|
| GEN-01 | GUI 调用与 CLI 共用同一生成核心；支持无 GUI 的 validate/generate，供 CI 使用。具体命令行名称待定。 |
| GEN-02 | 调用固定版本官方 Gen 生成 DDS 类型与序列化代码；不手写一套 CDR 序列化替代官方代码。 |
| GEN-03 | 自定义模板生成服务提供者/消费者接口及 App 端口装配、类型绑定等薄代码；可采用类似 Skeleton/Proxy 的职责划分，实际 API 名称按本产品规范定义。CM 队列、线程、匹配逻辑复用公共库。 |
| GEN-04 | 每个 App 有明确的发布/订阅接口；一个类型只生成一份共享类型实现，通过公共 target 复用，避免重复定义。 |
| GEN-05 | 输出依赖闭包与各 App 的 CMake target；业务只链接自身所需接口，不强制把所有 App 装进一个程序。 |
| GEN-06 | 固定输入、模板、工具版本、配置产生确定性内容；生成清单记录摘要和版本。可变时间/绝对路径不能无理由污染可复现代码。 |
| GEN-07 | 在临时目录生成并完成校验后发布整组产物；失败/取消保留上次成功版本，清理本次临时产物。跨平台实现须验证目录替换/回滚行为。 |
| GEN-08 | 按清单处理陈旧生成文件；只能管理受控生成目录，不能清空用户任意输出目录或覆盖手写业务文件。 |
| GEN-09 | 生成代码带来源标识，禁止手改；业务扩展位于独立手写目录，不以保留生成文件里的注释区作为主要维护方式。 |
| GEN-10 | 类型/拓扑的校验错误阻止发布，诊断包括编号、对象、路径与原因；进程退出码可供自动化判断。 |
| GEN-11 | 代码生成与编译分成两个动作。生成 C++ 不代表已有 ARM so 或 Windows DLL/LIB；构建阶段选择对应 SDK/工具链。 |
| GEN-12 | 生成集合绑定类型/模型/模板/Gen/SDK 基准摘要；构建时检查预期契约，避免头文件、配置和库来自不同生成批次。 |

建议产物结构（目录名称可调整，但所有权边界必须保留）：

```text
communication-project/
├── project.cm.json              # 逻辑工程源文件，Git 管理
├── types/*.cmtypes.json         # 类型契约源文件，Git 管理
├── deployment/*.json            # 可共享部署模板，Git 管理
├── config.local.json            # 工具路径/个人覆盖，忽略
├── business/                    # 手写逻辑，生成器不覆盖
└── out/<generation-id>/         # 受控生成目录，默认忽略
    ├── idl/
    ├── src-gen/
    │   ├── types/              # 官方类型与序列化生成物
    │   └── apps/               # 自定义 App 通信接口绑定
    ├── config/                 # 已解析通信配置/可选 DDS XML
    ├── metadata/               # 字段、单位、来源及兼容报告
    ├── cmake/
    └── generation-manifest.json
```

build-kit 现有 `dds generate --idl-set` 要求输入位于自身 idl 根目录，**尚不是任意外部工程生成入口**。实现时应选择扩展受控入口，或由新生成核心调用其锁定的 Gen 并自行实现临时目录/清单规则。不能默认把业务工程复制进 SDK 源码仓库，也不能把直接调用 Gen 误当作已经具备事务生成保障。

## 10. CM 运行库行为要求

### 10.1 API、所有权与线程

| 编号 | 要求 |
|---|---|
| CM-01 | 提供运行环境、发布端、订阅端的明确所有权和不可误复制的资源句柄；公开头文件不暴露 DDS 实体操作。业务类型的底层依赖边界须说明，不承诺无成本更换 DDS 实现。 |
| CM-02 | 创建失败返回具体错误并回滚已创建资源；业务 handler 在启用接收前注册；只有必需端点完成初始化才报告本地就绪。 |
| CM-03 | 异步发送入队成功、DDS 接纳、远端收到、业务完成分别定义；DDS 写入错误必须可观察。不能把一个 bool success 用于全部阶段。 |
| CM-04 | 若 API 声称非阻塞提交，底层 DDS write 不直接阻塞调用线程；定义队列满、关闭中、消息过大、资源不足的结果。不得把 DDS 异步发布模式当作绝对非阻塞保证。 |
| CM-05 | 消息跨线程投递具有明确所有权；不能存储临时参数引用或把已 return_loan 的数据交给业务。第一版可采用受控复制/移动，不默认保证零拷贝。 |
| CM-06 | DDS 接收路径与用户回调隔离；有界队列与可配置执行器；同一订阅默认顺序执行，跨订阅公平调度，慢回调策略明确。 |
| CM-07 | stop/cancel 幂等；停止接收新任务、处理或丢弃待处理任务的规则明确；等待已经运行的回调退出后才能销毁其依赖资源。回调内部请求停止不得等待自身。 |
| CM-08 | 对正在执行且不返回的用户回调，不能同时承诺强制有限时退出与安全销毁；需定义合作退出/超时报告，禁止静默分离悬空线程。 |

### 10.2 通信、资源与策略

| 编号 | 要求 |
|---|---|
| CM-09 | 同进程、同 Domain、同传输配置默认复用 Participant；配置不兼容时隔离。不要每个字段创建 Participant/Writer。 |
| CM-10 | 支持 UDP-only 与 UDP+SHM 配置；跨机使用可达网络，同机是否实际用 SHM 需测试。Data-sharing 单列，不与 SHM Transport 或零拷贝混同。 |
| CM-11 | 策略明确设置 Writer/Reader QoS、history、资源限制、发送/接收队列、溢出与超时行为；检查可靠性、durability、类型/表示等已支持的兼容约束。 |
| CM-12 | 队列具有消息数和字节上限；状态流可显式丢旧，事件/命令不得静默丢失。无界网络输入仍要有接纳与资源策略。 |
| CM-13 | 多订阅者状态使用正确计数/身份及同步；一个退出不阻止其他订阅者收取；无订阅者发送策略显式定义，不复制旧 live_flag 门控缺陷。 |
| CM-14 | Domain、实际 Topic、接口选择、发现地址/租期、传输和实例绑定可配置；缺失/不支持配置报错，展示最终有效值及来源。 |
| CM-15 | 不把所有配置承诺为热更新。第一版允许启动加载，修改需重建端点/重启时明确提示；环境变量/XML 的覆盖优先级要可追踪。 |
| CM-16 | 首版定义服务提供/停止提供、订阅/取消和可用性变化行为；服务实例身份、版本及本次运行会话可区分。按配置绑定实例，发布者重启后按约定恢复；不因某个 Event 有匹配者就判定整个服务业务健康。 |
| CM-17 | DDS 发现/端点状态到服务可用性的映射需明确证据和超时规则。若需补充服务元信息，使用产品版本化描述并纳入生成/互通验收，不隐藏在业务 payload 中或硬编码成感知协议。 |

建议状态流、事件/命令、记录流分开定义策略模板。DDS RELIABLE 不是执行确认；完整记录还依赖 DDS 之前的业务队列和后续记录能力。本版不承诺“永不丢包”或未经测量的硬实时。

### 10.3 状态、时间与诊断

| 编号 | 要求 |
|---|---|
| OBS-01 | 本地就绪、匹配数量、最后接收时间、数据过期分别报告；自订阅不能冒充远端在线，匹配也不能证明远端业务健康。 |
| OBS-02 | 记录提交、入队拒绝/替换、DDS 写入失败、接收、回调排队丢弃、字节量、队列高水位等本层可观测指标。 |
| OBS-03 | 如果协议提供源序号，按发布源及启动会话识别缺口；没有端到端证据时不声称所有网络丢包或业务处理情况都可被统计。 |
| OBS-04 | 元数据区分采集/发布/接收时间、时钟域与有效性；接收时间不替代源采集时间；跨设备时延需同步条件。 |
| OBS-05 | 提供日志/状态查询入口，定位 App 实例、端口、Topic、类型与配置摘要。CM 基础指标不强依赖 FASTDDS_STATISTICS 编译开关。 |

## 11. 独立产品与业务接入边界

PRODUCT-01：中间件独立开发、构建和验收，不依赖旧项目源码、旧生成代码、旧 Topic/binary 协议或现有上位机。原 COMPAT-01～04 已由用户新方向撤销，不再作为待实现需求。

PRODUCT-02：以自身 JSON/schema、生成接口、CM 运行库和版本化部署规则构成公开接入契约。业务与上位机按该契约提供/使用服务；业务内部结构转换由业务项目负责，不在通用 CM 中识别特定业务结构体。

PRODUCT-03：提供可运行的生产者、消费者及跨平台演示，用独立合成消息验证多类型、多实例和资源边界。API 文档说明如何填写消息与处理接收；样例不依赖真实设备才能演示基本通信。

PRODUCT-04：移除旧协议兼容不代表本产品发布后可以随意破坏接口。API、配置格式、类型/服务契约、wire 映射分别版本化，明确支持范围与迁移策略；类型变化和过期生成物必须可诊断。

PRODUCT-05：调试/诊断能力使用明确的接口与配置，不生成可无目标关闭全部业务发送的默认控制入口。首版没有 RPC 成功应答或业务执行保证，不用普通 Event 发布结果替代这些语义。

## 12. 构建、仓库与维护

BUILD-01：消费 build-kit 的锁定 SDK/CMake 导入目标；用户配置 SDK/工具链根目录，不写死 特定板卡名称或个人 SDK 路径。

BUILD-02：Linux native、AArch64 和 Windows 各有文档/脚本；明确 Gen 在开发机运行，目标代码分别编译。Windows DLL/LIB 属于构建/打包结果。

BUILD-03：GUI/CLI/模板/schema/运行库/样例/测试/文档版本受 Git 管理；个人配置、缓存、日志、编译产物和受控生成目录默认忽略。若发布生成代码，连同来源清单发布。

BUILD-04：共享 schema 和生成规则不能在 GUI、CLI、模板三处独立复制；给出从干净 clone 到示例收发的操作文档。首次准备允许下载工具和依赖，源码/工具版本按锁文件记录。

BUILD-05：SM 后续作系统/功能组状态决策；EM 执行应用启停等动作并报告结果，健康监督另行规划。CM 只提供通信与自身状态，模块依赖明确且无环；首版以架构文档保留边界，不预建无使用需求的全平台空模块。

## 14. 应交付什么

1. 带版本的 schema、模型说明、合法/非法样例和诊断编号。
2. 无 GUI 可运行的解析/校验/生成核心及 CLI，固定版本 Gen 集成。
3. 可视化编辑器，覆盖完整导入—建模—绑定—校验—生成流程。
4. 公共 CM 运行库、生成 App 接口模板和 CMake 接入方式。
5. 至少两种消息、多 App、多订阅者、多服务实例的独立可运行示例与新业务接入指南。
6. Linux/ARM/Windows 构建与验证记录，用户指南、接口行为/线程说明、故障排查与维护文档。
7. 各验收项完成/待测/受阻清单；不能用界面截图代替真实生成和通信结果。
8. AP 参考版本、职责/概念对应表、已实现范围及差异记录；核心依赖图和关键设计决策，支持后续扩展评审。

## 15. 建议实施顺序

1. **细化架构与契约：** D-01～D-05 已确认，不再重复询问。由设计方制定服务/Event 模型、schema v1、最小 API 和运行语义，明确模块依赖及独立验收负载。
2. **跑通最小生成链：** 候选 JSON → 校验 → IDL → 官方 Gen → 两个 App 接口，与最小 CM 一起编译收发；先验证模型可落地。
3. **落实运行约定：** 补有界队列、生命周期、错误、状态及相应失败路径验收。
4. **完成 GUI：** 接入同一核心，覆盖 App 编辑、导入与类型查看、连接配置、部署、诊断和生成。
5. **独立跨平台验收：** 用本产品样例验证 Windows 接收、同 SoC 传输、多实例和重启恢复，补资源测量与接入文档；旧业务迁移不进入首版验收。
6. **扩展：** 按需求加入更多导入器、请求应答与 SM；字段视图仅在未来明确要求时另行规划。

GUI 的流程原型可在前期用于评审，但产品验收以真实生成/运行链路为准。阶段 2 不能仅生成一个与后续 schema 无关的 HelloWorld 后声称生成器已完成。
